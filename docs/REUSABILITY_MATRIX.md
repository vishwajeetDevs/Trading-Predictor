# Reusability matrix

How to read the classifications:

| Classification | Meaning for this project |
| --- | --- |
| DIRECTLY REUSABLE | Can be called from the new backend with no change of market, session, or claim |
| REUSABLE WITH MODIFICATIONS | The algorithm is worth keeping, but the equity session, data source, or output claim must change before it is honest for BTC futures |
| ARCHITECTURAL REFERENCE ONLY | The shape is instructive. Reimplement it. Do not import the script |
| NOT REQUIRED | Specific to US stock selection, order execution, account sizing, or an unrelated public filing |

Nothing in this repository is a drop-in service for a Chrome extension. "DIRECTLY REUSABLE" below means a small pure function whose mathematics do not assume the NYSE. Even those should be copied into the new package with an MIT attribution comment, not imported across the clone, because the scripts are CLIs with side effects.

No row authorizes automated orders. Budget, risk, and broker stay out of the product.

## Summary

| Classification | Components |
| --- | --- |
| DIRECTLY REUSABLE | Wilder RSI(14) on a close series; percent-change helper; seeded RNG discipline as a practice |
| REUSABLE WITH MODIFICATIONS | True-range ATR (change the smoother and the session); SMA; close-confirmed level break; opening-range high/low as one session definition; dollar-volume ranking; bar-completeness filter; Time Machine ratio pool, horizon replay, and historical rule replay; news tag / dedupe / fingerprint state machine; alert condition evaluator |
| ARCHITECTURAL REFERENCE ONLY | JSON handoff between stages; pure-function core; offline vendor fixtures; partial-result reporting; freshness window on a quote; verdict that is allowed to say "coin flip"; refusal to invent a missing input |
| NOT REQUIRED | Nasdaq universe; Yahoo and Stooq clients as the data plane; NYSE holiday clock as the market clock; SEC 8-K and XBRL; House PTRs; Alpaca bracket sizing; pre-trade order gate; broker tickets; 13F weight splitter; long-only product policy; flat-by-the-close as a trading rule |

Realistic split of the ~8,600 lines of tool code: under 5% is small math that can move with light edits. About 15% is design worth reimplementing against Delta data. The rest is stock-session workflow or order execution and should not be carried into the extension.

## Questions the new product asks, and where the clone stands

| Product question | Closest existing piece | Verdict |
| --- | --- | --- |
| Is BTC bullish, bearish, or sideways? | SMA(20) cross and RSI buckets | Not a regime model. Build a stated definition (for example structure plus slope plus volatility band) and then measure how often that label matched the next horizon |
| Is a crash showing? | Nothing. RSI under 30 is not a crash test | Build from scratch: return percentile, ATR percentile, downside range expansion, and only if the data exists, liquidation and open-interest shocks |
| Is up or down becoming more likely? | Time Machine, but only for a chosen stop and target inside an NYSE afternoon | Rebuild resampling on BTC horizons. Report frequencies and sample size. Do not say "likely" without that table |
| Breakout or fake breakout? | First close above a level. No failure definition | Adapt the close-above test. Add "closed back inside within N bars" and the historical follow-through of each |
| Pullback or reversal? | `reclaim_ma20` and `oversold_bounce` only | Build structure (swing highs and lows) from scratch. Those two tags are not enough |
| Should the user wait? | Risk window and "coin flip" verdict | The verdict's humility is the right idea. The NYSE entry window is the wrong rule. "Wait" may only mean "the sample is small or the feeds are stale", unless a pre-registered condition says the historical follow-through was weak |
| Which prices should be watched? | Opening-range high, low, midpoint; caller level; alert rules | Adapt range levels and the alert evaluator. Add prior swing highs and lows, session high and low, and round numbers only when defined as a method |
| Scenarios at 15m, 30m, 1h, 4h, 24h | Time Machine terminal distribution for the rest of the cash session | Rebuild the simulator per horizon |
| What history supports it? | `history_replay` on about 60 sessions | Adapt the replay idea. Store a longer BTC history than 60 days so the count can be large enough to show |
| How confident and how reliable? | Seed, counts, and a verbal lean. No interval, no calibration | Build from scratch: sample size, interval or bootstrap, and later a calibration check of past statements against what the next horizon did |

## What not to do with this matrix

- Do not wrap `scan.py` or `timemachine.py` in FastAPI and point them at a BTC ticker. The session filter, the Yahoo URL, and the long-only plan schema would still be wrong.
- Do not loosen `trader-risk` so it accepts `BTCUSD` and then hide order routes behind the extension. That is a trading bot. It is out of scope.
- Do not retune stock constants (RSI 30, flag 10% and 5%, move 3%, 15-minute NYSE range, 1R coin-flip gap) by intuition and call them crypto parameters. If a threshold is used, it is a hypothesis to be measured on BTC history and reported with the sample.
